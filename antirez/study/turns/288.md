## Le 2 fasi dell'Evaluation nel Picture Language

### 1. Fase di Costruzione (Evaluator del Linguaggio Ospite)
Quando scrivi un'espressione come:
`const s_limit = square_limit(imgPainter, 2);`

L'evaluator del linguaggio ospite (il motore JavaScript o Scheme) valuta le espressioni ricorsive e costruisce un **albero di closure annidate**. 

In questa fase non viene disegnato un singolo pixel sul canvas. Il risultato di questa prima valutazione non è un'immagine, ma **un nuovo Painter** (ovvero una funzione che attende di ricevere un `frame`).

### 2. Fase di Rendering (L'Evaluator del Dominio "Picture")
L'effettiva valutazione del linguaggio figurativo avviene quando invochi la funzione finale passandole il frame di destinazione:
`s_limit(frame1);`

L'evaluator specifico del dominio Picture è composto da tre elementi che lavorano insieme:

* **Il meccanismo di dispatch delle closure:** Ogni combinatore (`beside`, `below`, `transform_painter`) agisce come una porzione dell'evaluator. Quando riceve il `frame1`, calcola i sotto-frame derivati e li passa a cascata ai sotto-pittori.
* **La funzione `frame_coord_map`:** È il cuore semantico dell'evaluator. Prende le coordinate astratte e adimensionati del dominio spaziale (l'intervallo $[0, 1] \times [0, 1]$) e le "valuta" (traduce) nelle coordinate geometriche reali definite dai vettori del frame.
* **I pittori primitivi (`segments_to_painter` / `image_to_painter`):** Rappresentano la base dell'evaluator, dove l'istruzione astratta si trasforma in un effetto collaterale concreto (la chiamata a `draw_line` o `ctx.drawImage` sulla Canvas API).

## Shallow Embedding vs Deep Embedding

Per capire perché l'evaluator sembra "invisibile" nel Capitolo 2, aiuta confrontare i due modi in cui si può progettare un DSL:

### Shallow Embedding (Quello usato in SICP Cap. 2)
Un *Painter* è rappresentato direttamente come una **procedura** `(frame) => void`. 
Poiché la sintassi del linguaggio coincide con la sintassi delle funzioni del linguaggio ospite, non c'è bisogno di scrivere un parser o un `switch/case` per interpretare i comandi. L'evaluator è la chiamata di funzione stessa.

### Deep Embedding (L'approccio tipico del Capitolo 4 e del C)
Se avessi rappresentato il Picture Language usando strutture dati astratte (AST), un *Painter* sarebbe stato un oggetto/struct:
`{ type: 'BESIDE', left: p1, right: p2 }`

In quel caso, l'evaluator sarebbe stato una funzione esplicita e centralizzata:
`​`​`typescript
function evaluate_picture(node: PictureAST, frame: Frame) {
  switch(node.type) {
    case 'BESIDE':
      // calcola sub-frame e chiama ricorsivamente evaluate_picture...
    case 'IMAGE':
      // disegna immagine...
  }
}
`​`​`
