## 🗺️ La Squadra di Attori nel Browser

Nel tuo player HLS per il web, la mappatura degli attori non sarà solo logica (all'interno di un unico loop), ma diventerà **hardware**, sfruttando i Web Worker come veri e propri thread isolati del tuo Mac/PC.

### 1. L'Attore Regista (Main Thread / UI)
* **Chi è:** Il file `main.js` classico.
* **Compito:** È l'unico che può toccare la pagina web (DOM). Gestisce i pulsanti di Play/Stop e mostra i log sullo schermo.
* **Mailbox:** Riceve eventi grafici dall'utente o messaggi dagli altri attori (es. `EV_AGGIORNA_BUFFER`).

### 2. L'Attore Rete (Web Worker #1)
* **Chi è:** Un Worker isolato (`network-worker.js`).
* **Compito:** Gira su un core separato della CPU. Fa il polling asincrono della playlist HLS e scarica i chunk `.ts` da Akamai.
* **Mailbox:** Riceve comandi dal regista (`START`, `STOP`). Quando scarica un chunk, "imbuca" il messaggio `EV_NUOVO_CHUNK` nella mailbox del Decoder.

### 3. L'Attore Decoder (Web Worker #2 + WebAssembly)
* **Chi è:** Un secondo Worker isolato (`decoder-worker.js`) che carica al suo interno il modulo **FFmpeg compilato in WASM**.
* **Compito:** Riceve i byte AAC crudi, li spinge dentro la pancia di WebAssembly (dove gira il codice C di FFmpeg velocissimo a basso livello) e sputa fuori i float decompressi.
* **Mailbox:** Riceve `EV_NUOVO_CHUNK`. Spedisce i float PCM decompressi direttamente alle casse del browser (tramite le Web Audio API o un `AudioWorklet`).

## 🔄 Il Viaggio del Dato: Un "postMessage" dopo l'altro

Guarda la pulizia concettuale di questo flusso. I thread non si scontrano mai su variabili comuni. Tutto si muove tramite la funzione nativa **`postMessage()`**, che agisce come il postino dell'Actor Model nel browser:

`​`​`text
[UTENTE_CLICCA_PLAY] 
       │
       ▼ (Main Thread invia postMessage)
[WORKER RETE] ──> Scarica l'array di byte AAC del chunk .ts
       │
       ▼ (Rete invia postMessage trasferendo la proprietà dei byte)
[WORKER DECODER] ──> Chiama la funzione C in WebAssembly ──> Decomprime in Float
       │
       ▼ (Decoder invia i float a)
[WEB AUDIO API] ──> Le casse del Mac suonano la radio
`​`​`

## ⚡ Perché questa combinazione è una superpotenza?

### 1. WebAssembly sposa l'Actor Model nativamente
Il modulo WASM (FFmpeg) ha la sua memoria privata isolata dal resto del browser (la *WASM Linear Memory*). Nessun codice JavaScript esterno può corromperla. Questa è la definizione perfetta di **Stato Privato dell'Attore**. Il Worker non fa altro che prendere i byte ricevuti dal messaggio, copiarli nella memoria di WASM, far fare i calcoli trigonometrici a FFmpeg e rispedire indietro il risultato.

### 2. Zero Lag sulla UI (Fluidità a 60 FPS)
Mentre FFmpeg in WebAssembly macina milioni di calcoli matematici per decodificare l'AAC e il Worker di rete combatte con la latenza di internet, il tuo Main Thread (la UI) è completamente vuoto e rilassato. La pagina web rimarrà fluida e reattiva al 100%, senza mai subire quei fastidiosi micro-freeze tipici delle web app pesanti.

### 3. Il passaggio di dati è a costo zero
Penserai: *"Ma passare megabyte di chunk audio via postMessage continuamente non rallenta il sistema a causa delle copie in memoria?"*. No, perché JavaScript permette i **Transferable Objects**. Quando il Worker di rete invia i byte al Decoder, puoi fare in modo che il browser non copi il buffer, ma sposti semplicemente la *proprietà* dell'indirizzo di memoria da un attore all'altro. Il passaggio diventa istantaneo (0 millisecondi).

## 🛠️ Da dove iniziare?

Il vero cuore di questo studio sarà la compilazione di FFmpeg in WebAssembly tramite **Emscripten** (il toolchain che trasforma il codice C in WASM). Esistono già build pronte di FFmpeg in WASM, ma compilarne una versione "minimal" (che contenga solo il demuxer MPEG-TS e il decoder AAC per pesare pochi kilobyte) ti darà una comprensione totale del ciclo di vita della memoria tra C e JavaScript.

Preferisci concentrarti prima sulla compilazione del modulo FFmpeg C in WebAssembly tramite Emscripten, o vuoi strutturare l'architettura dei messaggi `postMessage` tra i Web Worker usando JavaScript vanilla puro?
