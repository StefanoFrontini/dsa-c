## 🚫 Il Problema dei Sistemi Grafici (SDL3 / Cocoa)

Perché non puoi semplicemente mettere la UI dentro `poll()`?
Perché su sistemi operativi moderni come macOS (Cocoa) o Windows, gli eventi della tastiera e del mouse nell'interfaccia grafica **non sono associati a un semplice File Descriptor POSIX** che puoi dare in pasto a `poll()`. 

La coda degli eventi grafici di SDL3 viene gestita tramite API proprietarie del sistema operativo (come il RunLoop di Apple). Di conseguenza, non puoi scrivere:
`​`​`c
// ❌ QUESTO NON È POSSIBILE
fds[1].fd = SDL_GetEventFileDescriptor(); // Non esiste!
`​`​`

Se blocchi il thread dentro `poll()` per 5 secondi, la coda dei messaggi di macOS si riempie e l'applicazione crasha per mancata risposta.

## 🛠️ La Soluzione Industriale: L'Event Loop Non-Bloccante

Per far convivere rete, timer e grafica in un unico thread senza mai congelare nulla, l'architettura dei motori grafici (come i motori dei videogiochi o lo stesso browser) adotta una strategia diversa: **il polling non bloccante con timeout a zero (o quasi zero).**

Invece di lasciare che sia `poll()` a gestire l'attesa addormentando il thread, usiamo l'Event Loop per far girare continuamente il programma. Ad ogni ciclo facciamo un controllo rapidissimo (a costo zero) sia della grafica che della rete, e poi decidiamo noi di quanto riposare.

Ecco come si scrive questa coreografia in C:

`​`​`c
while (programma_attivo) {
    long long adesso = get_current_time_ms();

    // 1. GESTIONE GRAFICA (Non-Bloccante)
    // SDL_PollEvent controlla se l'utente ha cliccato, mosso il mouse o premuto tasti.
    // Se non ci sono eventi, ritorna immediatamente 0 senza bloccare.
    SDL_Event event;
    while (SDL_PollEvent(&event)) {
        if (event.type == SDL_EVENT_QUIT) {
            programma_attivo = 0;
        }
        // Qui invii i messaggi agli attori UI interessati...
    }

    // 2. GESTIONE RETE (Non-Bloccante)
    // Chiamiamo poll() con un timeout di ESATTAMENTE 0 millisecondi.
    // Significa: "Fai un controllo istantaneo dei socket. Se ci sono dati bene, 
    // altrimenti ritorna subito senza far dormire il thread".
    int res = poll(fds, num_fds, 0); 
    if (res > 0) {
        // Gestisci i dati in ingresso e invia i messaggi agli attori...
    }

    // 3. GESTIONE TIMER (Asincrona)
    // Controlliamo se il nostro timer da 5 secondi è scaduto
    if (retry_timer.active && adesso >= retry_timer.expiration_time) {
        retry_timer.active = 0;
        Event ev = { .type = EV_TIME_ELAPSED, .payload = NULL };
        send_message(retry_timer.target_actor, ev);
    }

    // 4. DISPATCHING DELLA MAILBOX
    svuota_mailbox_attori();

    // 5. IL MICRO-RIPOSO (La chiave per la CPU)
    // Se facessimo girare il ciclo while(1) all'infinito a vuoto, la CPU salirebbe al 100%.
    // Mettiamo un piccolissimo delay di 1 millisecondo. 
    // È impercettibile per l'essere umano, ma permette alla CPU di respirare.
    SDL_Delay(1); 
}
`​`​`

## ⚖️ Cosa abbiamo cambiato?

| Caratteristica | Modello con `poll()` bloccante | Modello Non-Bloccante (Timeout 0 + SDL_Delay) |
| :--- | :--- | :--- |
| **Pausa della CPU** | Gestita dal kernel dentro `poll(..., 5000)`. | Gestita da noi tramite `SDL_Delay(1)` ad ogni giro. |
| **Reattività UI** | **Pessima.** Si sblocca solo ogni 5 secondi o se arriva un pacchetto. | **Perfetta (60+ FPS).** La UI viene controllata e ridisegnata ogni millisecondo. |
| **Precisione Timer** | Alta, ma distruttiva per il resto del sistema. | Spaccata al millisecondo, senza bloccare nulla. |
| **Consumo CPU** | Praticamente 0%. | Praticamente 0% (grazie a `SDL_Delay(1)`). |

Questo approccio "non-blocking with tick delay" è il segreto con cui JavaScript nel browser riesce a gestire contemporaneamente le animazioni CSS, i clic dell'utente, i download di rete e i `setTimeout` senza mai mostrare un freeze della pagina. In C hai dovuto scrivere tu la logica del "regista", ma il principio fisico è lo stesso.
