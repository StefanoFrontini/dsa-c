### Slide 1: L'Abisso del Call Stack (La Matrioska)

**Titolo Slide:** *Il problema n.1: La Matrioska del Recursive Descent*

**Visivamente:**
A sinistra metti la nostra solita stringhina innocente: `[C]Ciao`
A destra, disegna una pila di blocchi verticali (il Call Stack) che mostra cosa deve fare un parser Recursive Descent per leggere quella singola parola rispettando le precedenze:

`​`​`text
1. parseSong()
   └── 2. parseLine()
        └── 3. parseExpression()
             └── 4. parseTerm()
                  └── 5. parseFactor()
                       └── BINGO! Trovato "[C]"
`​`​`

**Cosa dire alla platea:**
> *"Il Recursive Descent è Top-Down (dall'alto verso il basso). Questo significa che per capire che un pezzo di testo ha la precedenza assoluta (come il nostro accordo `[C]`), deve prima chiamare tutte le funzioni grammaticali superiori.*
> *Per leggere una singola parola, il motore JavaScript deve impilare 5 o 6 chiamate a funzione. In una canzone media ci sono circa 300 parole. Significa generare migliaia di funzioni annidate solo per spacchettare una stringa. È uno spreco di memoria e CPU atroce."*

### Slide 2: Il Paradosso della Moltiplicazione (Left Recursion)

**Titolo Slide:** *Il problema n.2: Il Loop Infinito (Left-Recursion)*

**Visivamente:**
Mostra due piccoli snippet di codice a confronto. Uno è la "Logica Umana" (che causa il crash), l'altro è la "Soluzione Algebrica" (il tuo parser).

**Snippet 1: L'Incubo Recursive Descent**
`​`​`javascript
// Grammatica: Una riga è formata da una parola, seguita da un'altra riga.
function parseLine() {
   const primaParola = parseWord();
   const restoDellaRiga = parseLine(); // <-- RICORSIONE!
   return unisci(primaParola, restoDellaRiga);
}
// Risultato su una frase lunga:
// RangeError: Maximum call stack size exceeded 💥
`​`​`

**Snippet 2: La Pace Algebrica (La tua Stack Machine / Reduce)**
`​`​`javascript
// Approccio Bottom-Up (La nostra equazione)
// Leggiamo da sinistra a destra in un ciclo piatto. ZERO ricorsione.
const line = parole.reduce((acc, parola) => acc + parola, EMPTY_LINE);
`​`​`

**Cosa dire alla platea:**
> *"Il secondo problema è la cosiddetta 'Left-Recursion' (Ricorsione Sinistra). Nel linguaggio naturale, le parole si susseguono l'una all'altra: Parola + Parola + Parola. 
> Se proviamo a scrivere questa regola in un parser Recursive Descent, la funzione continua a chiamare se stessa per scoprire quanto è lunga la riga, fino a far esplodere il Call Stack del browser con il temuto errore 'Maximum call stack size exceeded'.*
> 
> *Come lo abbiamo risolto noi? Ribaltando la prospettiva. Con lo Shunting-yard e l'approccio algebrico, non andiamo dall'alto verso il basso. Andiamo **da sinistra a destra** (Bottom-Up). Consumiamo un token alla volta, in un piattissimo, velocissimo e sicurissimo ciclo `while` o `reduce`. Zero chiamate annidate, zero crash."*

### La Chiusura del Discorso

Mostrando questi due limiti (profondità del Call Stack e Left Recursion), non stai solo giustificando la tua architettura, ma stai facendo divulgazione di altissimo livello. 

Stai insegnando al tuo pubblico che **il pattern giusto dipende dalla forma dei dati**:
* Dati fortemente incapsulati (es. JSON `{ "a": { "b": 1 } }`) $\rightarrow$ Recursive Descent va benissimo.
* Dati sequenziali con precedenze nascoste (es. Testo, Markdown, Formule $1 + 2 \times 3$) $\rightarrow$ Approccio Algebrico / Shunting-yard / Pratt.
