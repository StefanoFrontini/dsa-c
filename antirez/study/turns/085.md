  int precedence = getPrecedence(ctx);

  PObj *right = parseExpression(ctx, precedence);
  return createInfixObject(left, op, right);

PObj *parseExpression(pCtx *ctx, int precedence) {
  TokenType type = ctx->lexer.curToken.type;
  PrefixFn prefix = rulesTable[type].prefixFn;

  if (prefix == NULL) {
    printf("Error: Token %d cannot be used in prefix notation \n", type);
    return NULL;
  }

  PObj *left = prefix(ctx);

  while (ctx->lexer.curToken.type != TOKEN_ENDOFFILE &&
         precedence < getPrecedence(ctx)) {

    InfixFn infix = rulesTable[ctx->lexer.curToken.type].infixFn;
    printf("infix\n");

    if (infix == NULL) {
      return left;
    }

    left = infix(ctx, left);
  }
  return left;

La tua implementazione "sembra funzionare" per espressioni semplici come `(1 + 2)`, ma in realtà nasconde un **bug fatale di consumo dei token**. Se provi a parsare `(1 + 2) * 3`, il tuo parser si fermerà alla parentesi chiusa ignorando completamente il `* 3`!

Vediamo perché succede, e qual è la vera architettura "standard" per gestire il raggruppamento.

### Perché il tuo codice si ferma a metà?

Nel tuo codice, quando incontri `(`, chiami `parseExpression(ctx, -2)`. L'espressione interna viene valutata.
Quando il parser arriva a `)`, vede che la sua precedenza è `-1`. Poiché `-1 > -2` è falso (nella tua logica del `while`), il ciclo interno si ferma, ed è corretto.

**Ma chi ha consumato il token `)`? Nessuno!**
La funzione ritorna, ma `ctx->lexer.curToken` è ancora fermo su `)`. Quando il parser principale riprende, vede la `)` (che ha precedenza `-1`, inferiore allo 0 iniziale), chiude baracca e burattini, e termina il parsing restituendo l'AST, ignorando tutto il testo successivo.

### La Soluzione Elegante (La via del Pratt Parsing)

Il Pratt parsing gestisce le parentesi in modo geniale: **la parentesi chiusa non fa assolutamente nulla**. Serve solo come "muro" per fermare il parser, e poi viene consumata a mano. Inoltre, **non serve creare un nodo AST per le parentesi**.

Ecco i tre passi per l'implementazione corretta:

#### 1. Correggere la Tabella delle Regole
La parentesi chiusa non inizia un'espressione, quindi non deve avere una `prefixFn`. Inoltre, la precedenza delle parentesi nella tabella non importa (possiamo mettere 0), perché la loro logica è gestita diversamente.

#### 2. La Magia in `parsePrefix`
Quando troviamo una `(`, facciamo finta di far ripartire il parser da capo. Chiamiamo `parseExpression` passandogli **precedenza 0**. In questo modo, catturerà qualsiasi operatore interno.
Una volta catturato l'albero interno, **esigiamo** di trovare una `)` e la consumiamo.

### Perché non serve un nodo AST per le Parentesi?

Questo è uno dei concetti teorici più belli degli AST.
L'Abstract Syntax Tree descrive la struttura dell'espressione, *non* la sua formattazione testuale.

Prendi l'espressione: $1 + (2 \times 3)$
Il parser genererà questo albero: `INFIX( 1, '+', INFIX(2, '*', 3) )`.
Prendi l'espressione: $1 + 2 \times 3$
Genererà *esattamente lo stesso albero*, perché la moltiplicazione ha precedenza maggiore! Le parentesi nel primo caso erano ridondanti dal punto di vista matematico.

Prendi invece l'espressione: $(1 + 2) \times 3$
Quando il parser è dentro la parentesi, il `+` non viene sfidato dal `*` perché la parentesi chiusa funge da scudo. L'AST generato sarà automaticamente: `INFIX( INFIX(1, '+', 2), '*', 3 )`.
La struttura ad albero *garantisce* da sola l'ordine di risoluzione (dal basso verso l'alto). Le parentesi servono solo al Lexer/Parser per forzare questa struttura, ma una volta costruito l'albero, hanno esaurito la loro utilità e svaniscono nel nulla.

Implementando questa logica, il tuo parser è in grado di risolvere espressioni di profondità arbitraria come `-( (1 + 2) * (3 / -(4 + 5)) )`.
