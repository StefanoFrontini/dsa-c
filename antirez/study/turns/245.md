## 📦 Le Strutture Dati Principali

Per far girare questo sistema hai bisogno di tre sole strutture dati fondamentali. Nota come siano incredibilmente leggere ed esenti da qualsiasi riferimento a `pthread_mutex_t` o `pthread_cond_t`.

### 1. L'Evento (Il Messaggio)
È una semplice `struct` che trasporta l'informazione. Ha un'enumerazione per capire *cos'è* il messaggio e un puntatore generico per i dati associati.
`​`​`c
typedef enum {
    EV_AVVIA_DOWNLOAD,
    EV_CHUNK_SCARICATO,
    EV_RICHIESTA_BYTE,
    EV_PLAY,
    EV_STOP
} EventType;

typedef struct {
    EventType type;
    void *payload; // Può puntare a una stringa URL, a un chunk di byte, ecc.
} Event;
`​`​`

### 2. La Mailbox (La Coda)
Un banalissimo Ring Buffer logico di eventi. Non serve sincronizzazione perché un solo thread scriverà e leggerà da qui.
`​`​`c
#define MAX_MAILBOX_SIZE 32

typedef struct {
    Event eventi[MAX_MAILBOX_SIZE];
    int head;
    int tail;
} Mailbox;
`​`​`

### 3. L'Attore
L'oggetto atomico del tuo programma. Contiene il suo stato logico attuale, la sua mailbox privata e il puntatore alla sua **funzione comportamento**.
`​`​`c
struct Actor; // Forward declaration

typedef void (*BehaviorFn)(struct Actor *self, Event ev);

typedef struct Actor {
    int id;
    int stato_attuale;   // Gestito dalle enum degli stati (es. IDLE, DOWNLOADING)
    Mailbox mailbox;
    BehaviorFn receive;  // La funzione di transizione della macchina a stati
    void *local_context; // Memoria privata dell'attore (es. il buffer audio per l'attore Buffer)
} Actor;
`​`​`

## 🏛️ La Logica di Invio: `send_message`

Inviare un messaggio diventa un'operazione istantanea, sicura e a costo CPU quasi zero. Significa fare una `push` nella mailbox dell'attore di destinazione:

`​`​`c
void send_message(Actor *destinatario, Event ev) {
    // Inserisce l'evento nella mailbox del destinatario
    destinatario->mailbox.eventi[destinatario->mailbox.head] = ev;
    destinatario->mailbox.head = (destinatario->mailbox.head + 1) % MAX_MAILBOX_SIZE;
}
`​`​`

## 🔄 Il Ciclo Centrale: L'Event Loop

Il tuo `main` si trasforma nel regista del tempo. Il suo unico compito è girare in un ciclo infinito, controllare chi ha "lettere" nella cassetta postale e fargli eseguire la sua funzione comportamento, una alla volta.

`​`​`c
// L'Event Loop Centrale
while (programma_attivo) {
    
    // 1. Fase di Polling Non-Bloccante (L'Hardware che genera Eventi)
    gestisci_I_O_non_bloccante_rete(actor_network);
    gestisci_I_O_non_bloccante_audio(actor_player);

    // 2. Fase di Dispatching dei Messaggi tra Attori
    for (int i = 0; i < NUM_ATTORI; i++) {
        Actor *attore = &squadra_attori[i];
        
        // Se l'attore ha messaggi da leggere nella sua mailbox...
        while (attore->mailbox.head != attore->mailbox.tail) {
            // Estrae l'evento
            Event ev = attore->mailbox.eventi[attore->mailbox.tail];
            attore->mailbox.tail = (attore->mailbox.tail + 1) % MAX_MAILBOX_SIZE;
            
            // Scatta la transizione di stato dell'attore!
            attore->receive(attore, ev); 
        }
    }
    
    // Un micro-riposo per non far schizzare la CPU del Mac al 100% se non c'è lavoro
    SDL_Delay(1); 
}
`​`​`

## 🗺️ Gli Step Implementativi e il "Segreto" dell'I/O Asincrono

Il vero scoglio ingegneristico di questa riscrittura non è la gestione degli attori, ma la **gestione dell'I/O non bloccante**. Se un attore esegue una funzione che si blocca (come la vecchia `SSL_read` o `connect`), **l'intero Event Loop si congela**, e la musica si ferma istantaneamente.

Per farlo funzionare in un singolo thread devi convertire la rete e l'audio in modalità asincrona:

### Step 1: L'Attore Rete e i Socket Non-Bloccanti
Devi impostare il socket TCP in modalità non bloccante (`fcntl(sockfd, F_SETFL, O_NONBLOCK)`). 
* Nella fase 1 dell'Event Loop, userai la chiamata di sistema `select()` o `poll()`. 
* Chiederai al kernel del Mac: *"Ci sono nuovi byte sul socket in questo millisecondo?"*.
* Se la risposta è **No**, l'Event Loop passa oltre immediatamente.
* Se la risposta è **Sì**, leggi quel piccolo chunk di byte e invii un messaggio `EV_DATI_RICEVUTI` all'Attore Buffer.

### Step 2: L'Attore Player e la Coda SDL3
Invece di avere un ciclo che decodifica continuamente, l'Attore Player si regola interrogando SDL3 in modo non bloccante ad ogni giro dell'Event Loop.
* Chiede a SDL: *"Quanti secondi di audio ci sono in coda?"* (`SDL_GetAudioStreamQueued`).
* Se la coda è bassa, invia un messaggio `EV_RICHIESTA_BYTE` all'Attore Buffer.
* Se l'Attore Buffer risponde inviando i byte AAC nella mailbox del Player, quest'ultimo si attiva, chiama FFmpeg, genera i float e li spinge in SDL, per poi tornare in stato di guardia.

## 💎 Perché questo modello è un capolavoro di pulizia

Se implementi questo sistema, noterai che la funzione `receive(Actor *self, Event ev)` di ogni attore conterrà solo ed esclusivamente un grande `switch(self->stato_attuale)` combinato con un `switch(ev.type)`. 

La logica del tuo lettore musicale diventerà una griglia geometrica bidimensionale perfetta, totalmente separata dalla gestione dell'hardware. Se c'è un bug, sai matematicamente che si trova in una specifica transizione di stato di un singolo attore isolato.
