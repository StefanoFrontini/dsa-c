No, **non è affatto normale**. Hai un'ottima vista e hai beccato uno dei problemi più subdoli della programmazione in C: una **perdita di memoria (Memory Leak)**.

Un player audio o qualsiasi applicazione di streaming, dopo una fase iniziale di assestamento (caricamento delle librerie, allocazione del Ring Buffer), deve raggiungere un plateau stabile (es. fissarsi a 32-34 MB) e **rimanere piatto per ore**. Se la memoria continua a salire incessantemente, significa che il tuo programma alloca nuove risorse a ogni ciclo ma si dimentica di restituirle al sistema operativo.

Analizzando approfonditamente il codice che mi hai mostrato prima, il colpevole è chiarissimo ed è nascosto nella gestione della rete.

## 🕵️ Il Colpevole: Il ciclo di vita di `fetch()`

Ogni volta che lo spazio scende sotto la soglia, il tuo thread di rete (`get_data`) esegue questo ciclo:
1. Imposta lo stato a `INIT_CONNECTION`.
2. Chiama la funzione `fetch(ctx)`.
3. `fetch` chiama `initConnection(ctx)`, che esegue:
   `​`​`c
   ctx->conn.ssl_handle = SSL_new(ctx->conn.ssl_ctx);
   `​`​`
4. Scarica i file e, quando ha finito tutto con successo, la macchina a stati atterra qui:
   `​`​`c
   case DONE:
       return;  // Uscita dalla funzione fetch
   `​`​`

### Ecco dove si nasconde il leak:
Quando la `fetch` termina con successo ed esce con `return`, **il socket TCP e l'handle di OpenSSL (`ssl_handle`) rimangono aperti e allocati nell'Heap!** Nessuno li chiude alla fine di una richiesta andata a buon fine.

Al giro successivo, il thread di rete chiama nuovamente `fetch`, che riesegue `initConnection` e sovrascrive il puntatore `ctx->conn.ssl_handle = SSL_new(...)` con una nuova connessione. La memoria della vecchia sessione TLS e il vecchio descrittore del socket vengono abbandonati nell'Heap, diventando invisibili ma occupando spazio. Visto che la radio scarica continuamente piccoli chunk ogni pochi secondi, la memoria sale come un tassametro.

## 🛠️ Come tappare la falla

Dobbiamo assicurarci che, ogni volta che la funzione `fetch` finisce il suo lavoro (sia che esca con successo, sia che esca per un errore), la connessione di rete e la memoria associata a OpenSSL vengano distrutte prima di restituire il controllo al thread.

Il posto migliore in cui inserire questo "freno di pulizia" è nel ciclo del tuo thread **`get_data`**, subito dopo la chiamata a `fetch`:

`​`​`c
void *get_data(void *arg) {
  Ctx *ctx = (Ctx *)arg;

  while (1) {
    // ... (il tuo codice di controllo della soglia con i mutex) ...

    printf("\n Fetching data...\n");
    ctx->parser.state = INIT_CONNECTION;
    ctx->parser.resource = MASTER_PLAYLIST;
    
    fetch(ctx); // Esegue la richiesta di rete

    // --- NUOVO: TAPPIAMO IL MEMORY LEAK QUI! ---
    // Ogni volta che fetch(ctx) finisce (ritorna), puliamo la connessione appena usata
    if (ctx->conn.ssl_handle) {
        SSL_shutdown(ctx->conn.ssl_handle);
        SSL_free(ctx->conn.ssl_handle);
        ctx->conn.ssl_handle = NULL; // Evita dangling pointers
    }
    if (ctx->conn.sockfd >= 0) {
        close(ctx->conn.sockfd);
        ctx->conn.sockfd = -1;
    }
    // --------------------------------------------

    pthread_mutex_lock(&audio_buffer_mutex);
    pthread_cond_signal(&audio_buffer_threshold_cv);
    pthread_mutex_unlock(&audio_buffer_mutex);
  }
}
`​`​`

### Un piccolo dettaglio correlato:
Visto che ora pulisci la connessione alla fine di ogni `fetch` direttamente nel thread, puoi rimuovere la pulizia che facevi parzialmente nello stato `RECONNECT` all'interno della `fetch`, lasciando che quel *case* si occupi solo di resettare lo stato logico del parser prima di rilanciare la connessione.
